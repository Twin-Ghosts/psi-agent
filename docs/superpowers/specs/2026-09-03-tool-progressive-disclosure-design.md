# 工具按需暴露（渐进披露）· 下批设计

> 姊妹文档：`docs/superpowers/specs/2026-09-03-request-assembly-budget-design.md`（本批，装配点预算化与前缀缓存稳定化）。
> 分工：那一份让请求大小有归属、并把前缀稳定下来（**不减工具，210 个照发**）；本份评估削减工具数量本身。

## 结论

1. **必须单独成批，不能与本批合并。** 两者收益方向相反：本批冻结 `tools` 数组以换缓存命中，本设计减少工具以换字符数 —— 而**减工具必然打掉缓存**。合批做则观测到的变化无法归因。
2. **底座已经存在且在线上跑着。** `tool_search` / `tool_describe` / `tool_search_code` 三个元工具已在 git 里，生产跑的就是仓库版本（md5 完全一致）。要做的是「让装配点用上它」，不是从零造。
3. **但本设计的预期收益可能很小，甚至不值得做。** 上游 TTFB 实测只有 **0.18 秒** —— 工具 schema 大小从来不是延迟瓶颈（真瓶颈是 30 秒钩子超时、每回合 38 秒压缩、排队 p50 169 秒）。而在本批缓存生效后，285566 字符若已 99.7% 命中，再省字符数的边际收益有限。
4. **因此本文档的建议是：等本批上线并量到缓存命中率之后再决定是否启动。** 若命中率达标，本设计应当被**主动放弃**而非硬推。
5. **两个已核实的拦路问题**：仓库里存在与按需暴露**直接矛盾**的反向指引（`prompt_sections.py:503,521` 明确要求模型不要调 `tool_describe` / `tool_search_code`）；元工具是**双份**的，且只有一侧有测试。

## W —— 是什么

### 1. 为什么单独成批（本文档的立论）

**归因冲突。** 本批件一B 冻结 `tools` 数组，目标是把 `prompt_cache_hit_tokens / prompt_tokens` 的命中率拉上去，工具数量保持 210 不动 —— 靠缓存把 285566 字符**变便宜**，而不是变没有。本设计的目标是减少发送字符数，一旦工具集合随会话变化就必然打掉缓存。两者混在一起，观测到的延迟变化分不清是缓存生效还是字符变少。

这个仓库刚为归因不清栽过一次：2026-09-02 报出的「一句你好 135 秒 → 24 秒，5.6 倍」，被次日 14 小时观测推翻 —— 真人会话 p50 只从 8361 降到 7813 ms，p90 反而从 25542 **恶化**到 38239 ms，因为改后样本被单个会话占了 71%。

**验证类别不同。** 减工具要验的是「**能力没丢**」，那是行为验证；本批的判据是结构性的（请求装不出超限、wire 形状合法、缓存命中率）。两类判据不能共用一批用例。

**风险类别不同。** 本批改错了会立刻可见（请求失败、命中率判据变红）。减工具改错了是**模型静默降级** —— 它不再知道某个能力存在，于是绕路或直接告诉用户做不到，可能几天后才被人发现。这类风险必须单独观察，不能藏在别的改动后面。

### 2. 实测前提

2026-09-03 在生产机对 deepseek-v4-flash 实测前缀缓存（完整 6 行数据见姊妹文档 W 段第 2 节）。对本文档最关键的是 **R4**：

| 探测 | prompt_tokens | cache_hit | cache_miss |
|---|---|---|---|
| R2 原样重发 | 19519 | 19456 | 63 |
| **R4 删掉 1 个工具（8 → 7）** | **19444** | **13568** | **5876** |
| R5 工具恢复 8 个 | 19519 | 19456 | 63 |

工具区仅占 body 的 **0.7%**，删掉其中一个就让命中从 19456 掉到 13568，损失 **5888 token**。

**据此本设计的硬前提是：工具集合必须在一个会话内保持稳定。** 任何「按需追加」的做法都要正面回答「变一次赔一次缓存」这笔账。

两条**不得越界**的解读：

- R4 的 69.8% **不能**外推成「减工具只赔 30%」。那是 8 个工具规模下的比例，必须按比例而非按绝对值理解。生产 210 工具 / 285566 字符的规模下，工具集合一变**几乎等于缓存全失**。
- `tools` 在序列化中的**确切位置未测定**（13568 恰为 212×64，块对齐，单点不足以定位）。本文档只声称它参与缓存键、改动会打掉一大片，**不声称**它排在 `messages` 之前。

### 3. 现状与现成基础设施（2026-09-03 已核实）

生产 210 个工具全量注入，schema 约 285566 字符。装配点在 `src/psi_agent/session/agent.py:688-708`，`tool_defs` 由 `self._tool_registry.tools.values()` 全量展开（注册在 `session/tool_registry.py:450` `load`）。

**三个元工具已在 git 里，且已在生产运行。** 落点是**双份**：

| 路径 | 三个文件 | 测试 |
|---|---|---|
| `agents/feishu/tools/` | 齐全 | `agents/feishu/tests/test_tool_discovery.py` |
| `agents/desktop/tools/` | 齐全 | **无** |

三对文件当前逐字节相同（md5 前 8 位：`tool_search.py` `b313dfcc`、`tool_describe.py` `15b0ed96`、`tool_search_code.py` `edb5d509`）。生产 `/srv/haitun/psi-agent/workspace/tools/` 下三个文件的 md5 **与 git 完全一致** —— 生产跑的就是仓库版本，没有本地改动。

已核实的签名：

```python
async def tool_search(query: str, limit: int = 20) -> str          # tool_search.py:22
async def tool_describe(name: str) -> str                          # tool_describe.py:22
async def tool_search_code(pattern: str, limit: int = 50,
                           ignore_case: bool = True) -> str        # tool_search_code.py:23
```

`tool_search` 与 `tool_search_code` 都已自带截断提示（`[Truncated at N results — narrow the query for more]`），这是「检索返回过多」这一失败模式的现成兜底。

`agents/feishu/tests/test_tool_discovery.py:48` 断言 `{"tool_search", "tool_search_code", "tool_describe"} <= names`，并覆盖了 `tool_search_code` 的**无效正则回退**（`:1716`，不平衡括号）。

> **路径澄清**：主检出**没有** `examples/haitun-workspace/tools/`。该路径只存在于 `.claude/worktrees/recovery-doc`（分支 `docs/external-container-recovery-plan`）这个无关 worktree 里，**不要引用它**。这正是「Kanban worktree 里 git 命令会静默落到别处」那类坑。

### 4. 验收标准

本批（件五）若启动，须满足全部四条：

| # | 验收标准 |
|---|---|
| V1 | `tools` 数组在**一个会话内字节不变**（否则赔掉缓存，直接判负） |
| V2 | 构造一组必须用到**非核心工具**才能完成的任务，模型仍能完成 |
| V3 | 模型不调 `tool_search` 就宣称做不到的情形有判据覆盖 |
| V4 | `prompt_cache_hit_tokens / prompt_tokens` 不低于本批上线后量到的基线 |

**V2 必须做变异复核**：故意把某个工具从可检索集合里摘掉，断言用例**真的变红**。绿而不吃劲的用例在这个仓库出过事 —— 一个分支撞四次兜底分支，提前吃掉了结论。

## H —— 怎么做

### 1. 三种形态的账

| 形态 | 工具数组 | 缓存 | 代价 |
|---|---|---|---|
| **A 静态分层** —— 会话开始时按 workspace 配置定一组，会话内不变 | 恒定 | 友好 | 要人工维护分层；分错则能力丢失且不自愈 |
| **B 元工具检索** —— 只暴露少量核心工具 + `tool_search` / `tool_describe`，模型按需查 | 恒定 | 友好 | 多一次往返；依赖模型会用；底座已存在 |
| **C 动态追加** —— 用过的工具留在数组里（即 M2 的形状） | **每遇新工具就变** | **每变一次全失** | **已被 R4 实测判死** |

**C 已被排除。** M2 线上日志 `tools_exposed=53 of 210` 而白名单只有 49 个，说明 `_tmpfix_seen` 已涨了 4 个 —— 即已发生至少 4 次缓存作废。它省的是字符数，赔的是 99.7% 的命中率。本批部署时 M2 连同其余 5 项一起回滚到 `.orig` 基线。

**A 与 B 都满足 V1。** B 的底座现成（第 3 节），且不需要人工维护分层，是首选；A 可作为 B 的补充（核心层用静态配置定义）。

### 2. 拦路问题一：反向指引与按需暴露直接矛盾

`agents/feishu/systems/prompt_sections.py` 有两处明确要求模型**不要**去查：

- `:503` —— `Do not reread the skill, call \`tool_describe\`, call \`feishu_task_create\`, or send another card/message.`
- `:521` —— `` `form_value.custom_reply`; do not call `tool_describe`, `tool_search_code`, `read`, or `bash` to rediscover its action ``

**一边叫模型别去查，一边又指望它按需查。** 这个矛盾必须在实现前正面处理，否则按需暴露上线即自相矛盾：模型在这些场景下拿不到工具定义、又被禁止检索，只能猜或放弃。

处理方向（需在实现时定夺）：把这两处指引**收窄到具体场景**（它们原意是防止某个已知流程里的重复发现，不是全局禁令），而不是删掉 —— 它们各自对应过真实事故，`agents/feishu/tests/test_prompt_sections.py:120` 还有断言守着 `:521` 那句。改它就要同步改那条测试，**且要说明为什么放宽是安全的**。

### 3. 拦路问题二：双包重复

同一份元工具在 `agents/desktop/` 与 `agents/feishu/` 各存一份，**且只有 feishu 一侧有测试**。

这个仓库已经因为双包拆分吃过亏：上游改动只跟到一侧（desktop 拿新版 feishu 留旧版），而 git 的落点建议本身也会错。三对文件**当前**逐字节相同，但没有任何机制保证它们继续相同。

本设计须明确选一条并写清理由与代价：

- **收敛成一份共享实现** —— 根治漂移，但要动两个包的加载路径，范围外溢。
- **保持两份 + 判据同时覆盖两侧** —— 范围小，但要补 desktop 侧缺失的 `test_tool_discovery.py`，且需要一条守同步的判据（例如断言两侧内容一致）。

**不可以默默只改一侧。**

### 4. 收益上限估算 —— 本设计可能不该做

这一节是本文档最重要的部分。

**延迟维度：工具 schema 不是瓶颈。** 上游 TTFB 实测 **0.18 秒**。已归因的真实成本是：30 秒钩子超时、每回合 38 秒压缩、排队 p50 169 秒（8-31 恶化到 774 秒，元凶是 49 轮失控回合霸占锁）。批一上线后 hook 超时归零，压缩 41.5s×22 次成了新头号成本。**这些没有一项与工具 schema 大小相关。**

**成本维度：缓存已经把它变便宜了。** 若本批上线后 285566 字符稳定命中，命中 token 的计价远低于 miss。减工具能省的是「已经打了折的那部分」，边际收益有限。

**风险维度：唯一会引入静默能力损失的一批。** 本批所有改动改错了都立刻可见；本设计改错了几天后才发现。

**因此建议**：本批上线后先量三个数 —— 缓存命中率、压缩耗时占比、排队 p50。**若命中率达标，本设计应被主动放弃**，把力气放到压缩与排队上（那才是量到的头号成本）。这不是消极，是把「不做」也当成一个正当结论。

**若仍决定做**，则形态取 B，范围限定为「让装配点从全量展开改为读一份会话内恒定的核心集合 + 三个元工具」，并先解决第 2、3 节两个拦路问题。

## T —— 测试与验收

### 1. 能力不丢怎么验（本设计与本批最大的差别）

`agents/feishu/tests/test_tool_discovery.py` 可作起点，**但需先判断它验的是「注册」还是「暴露」** —— 这两件事在本设计里会分开：工具仍然全部注册（`tool_registry` 不变），只是不再全部**暴露**给模型。现有断言 `{"tool_search", "tool_search_code", "tool_describe"} <= names` 验的是注册，**过不了本设计的关**。

需新增的判据：

- **V2 正向**：构造必须用非核心工具才能完成的任务，断言完成。
- **V2 变异**：把该工具从可检索集合摘掉，断言用例变红。
- **V3**：断言模型在核心集合不够用时会调 `tool_search`，而不是直接宣称做不到。

### 2. 元工具自身的失败模式

| 失败模式 | 判据方向 | 现状 |
|---|---|---|
| 模型不调 `tool_search`，直接说做不到 | V3 | 无覆盖，需新增 |
| 检索词与工具名对不上 | 断言同义/近义词能命中 | 无覆盖，需新增 |
| 检索返回过多 | 断言截断提示出现 | **已有兜底**：`[Truncated at N results …]` |
| 无效正则 | 断言回退不抛异常 | **已有测试**：`test_tool_discovery.py:1716` |

### 3. 边界与非目标

- **本文档不改本批任何设计**，不重复本批的现状核查与临时改动清单。
- **减工具不解决固定开销中的系统提示部分**（生产系统提示 181218 字符，约 117k token）。两者是两笔账。本批已指出：默认预算 `100000` 小于固定开销约 117k，**必须先把预算默认值提到固定开销之上**，那是本批的事。
- **换算参考**：中文密集文本约 1.56 字符/token，JSON 类 ASCII 内容约 3.5-4 字符/token。**工具 schema 以 ASCII 为主，折算时不可用中文比值。**
- **外部资料未能核实**：调研业界渐进披露做法时，`modelcontextprotocol.io` 等六个来源全部被抓取拦截，只拿到搜索摘要，**正文未读**。本文档因此**不引用任何外部数字**。若后续补充，凡引用外部数字必须标注「未核实，来源仅摘要」，不得把摘要里的数字当实测写。
