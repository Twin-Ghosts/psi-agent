# 任务安排反馈机制设计

**日期**: 2026-08-01  
**状态**: 草案  
**范围**: `Dolphin-Agent` 侧工作流与 `fusion_memory` 侧组织记忆数据模型

## 1. 背景

当前任务安排已经能把安排者的原始输入整理成可共享的工作安排，并通过飞书卡片发给接收者。但在真实协作里，接收者经常会在理解任务、形成方案、推进执行的过程中遇到缺口：

- 缺少只有安排者能确认的信息
- 需要安排者做一个会影响范围或结果的决定
- 需要对齐后才能继续执行
- 需要保留原始答复、共享结论、后续修订的完整链路

如果这些信息只靠聊天转述，容易丢背景、打断对话，或者把推测写成事实。

## 2. 目标

1. 任务安排中的“反馈”作为独立对象管理，不并入既有 `assignment_transition` 主状态机。
2. 同一条反馈以 `arrangement_id` 为主键，`task_id` 可后绑。
3. 安排者和接收者都能查看同一条反馈，但字段级可见性不同。
4. 原始答复必须保留，不可覆盖，只能追加版本。
5. 默认情况下，安排者补充答复后进入“已更新、待接收者确认”，不能自动恢复执行。
6. 卡片只保留一张活跃实例，后续状态通过更新原卡片完成，不重复发送。
7. Agent 侧只保留一个高内聚的反馈入口，不做一组细碎 tools。

## 3. 非目标

- 不做独立的权限系统重构。
- 不做新的卡片组件框架，复用现有飞书卡片发送/更新能力。
- 不把反馈逻辑塞回 `assignment_transition` 里。
- 不把反馈限制在开发任务场景，通用工作安排都适用。

## 4. 总体方案

采用“共享反馈线程 + 追加式反馈条目”的结构。

- `feedback_thread` 表示一条任务安排下的当前反馈状态。
- `feedback_entry` 表示一次反馈、一次答复、一次分析或一次确认。
- 所有条目按版本追加，不覆盖旧内容。
- 线程级状态只表示“当前该怎么处理”，不替代历史。

推荐的状态：

- `open`
- `blocked`
- `updated_waiting_recipient_confirmation`
- `ready_to_execute`
- `resolved`

其中 `updated_waiting_recipient_confirmation` 是默认恢复态：安排者补充后，Agent 只更新理解，不直接放行执行。

## 5. 数据模型

### 5.1 FeedbackThread

| 字段 | 说明 |
|---|---|
| `thread_id` | 线程主键 |
| `organization_id` | 组织 ID |
| `arrangement_id` | 任务安排主键，线程主键语义上的归属点 |
| `task_id` | 飞书任务 ID，允许后绑 |
| `state` | 当前状态 |
| `latest_shared_summary` | 最近一次对双方可见的共享结论 |
| `latest_agent_analysis` | 最近一次 Agent 的理解与拆解 |
| `latest_missing_items` | 当前仍缺失的信息 |
| `current_card_id` | 活跃卡片 ID |
| `version` | 线程版本 |
| `created_at` / `updated_at` | 时间戳 |

### 5.2 FeedbackEntry

| 字段 | 说明 |
|---|---|
| `entry_id` | 条目主键 |
| `thread_id` | 所属线程 |
| `parent_entry_id` | 可选，指向上一版本或关联条目 |
| `author_role` | `assigner` / `recipient` / `agent` / `system` |
| `kind` | `question` / `response` / `analysis` / `plan_delta` / `confirmation` / `private_note` |
| `visibility` | `shared` / `assigner_private` / `recipient_private` / `agent_only` |
| `raw_content` | 原始内容，必须保留 |
| `shared_content` | 脱敏或整理后的共享内容 |
| `revision` | 版本号，追加不覆盖 |
| `created_at` | 时间戳 |

### 5.3 关键约束

- `raw_content` 永远不改写。
- 如果某条私密补充会改变执行条件，系统必须产出可共享结论，或者继续保持阻塞。
- `task_id` 可以为空，等正式飞书任务创建后再绑定。
- 同一 `arrangement_id` 下可以有多条 `feedback_entry`，但只应有一张活跃卡片。

## 6. 反馈判定

### 6.1 阻塞反馈

只有以下情况才算阻塞：

- 只有安排者才能提供的必要信息
- 需要安排者做不可逆或明显影响范围的决定
- 权限、资源或需求冲突导致无法继续
- 继续推断可能造成显著返工或越权

如果 Agent 能用明确、可逆、可记录的假设继续推进，就不应标成阻塞。

### 6.2 非阻塞反馈

这类反馈不立即打断当前对话，但会被写入线程，等到里程碑、固定时间，或安排者会话空闲时再集中提醒。

### 6.3 纯信息记录

只写入线程日志，不提醒安排者。

## 7. 交互流程

### 7.1 生成反馈

1. Agent 发现缺口。
2. 先检查是否能通过搜索、历史任务、仓库或文档补齐。
3. 仍不能补齐时，生成 `feedback_thread` 或在现有线程上追加新条目。
4. 若是阻塞反馈，立即发一张飞书卡片给安排者。
5. 卡片内容只展示当前缺口、共享理解和下一步动作，不重复刷新新卡。

### 7.2 安排者答复

安排者通过卡片快捷选项或补充说明回复后：

- 原始答复追加到 `feedback_entry`
- 线程状态进入 `updated_waiting_recipient_confirmation`
- Agent 更新理解，但不自动恢复执行

### 7.3 接收者确认

接收者看到的是同一条反馈线程的更新结果，而不是新开一条消息。

只有接收者确认后，线程才能进入 `ready_to_execute`，接收者侧的执行流程才继续。

### 7.4 卡片策略

- 只允许一个活跃卡片实例
- 后续变化通过更新原卡片完成
- 避免在长会话中重复发送同类卡片

## 8. Agent 与 Memory 分工

### 8.1 Memory 负责

- 保存线程和条目
- 保留版本和历史
- 维护状态机
- 维护字段级可见性
- 记录卡片原位更新所需的信息

### 8.2 Agent 负责

- 判断是否该生成反馈
- 判断是阻塞、非阻塞还是纯记录
- 将原始输入整理成共享版结论
- 在收到答复后更新任务理解
- 决定何时发卡、何时更新卡、何时等待接收者确认

### 8.3 Tool 形态

Agent 侧只保留一个反馈管理入口，内部用 `action` 区分：

- `create`
- `append`
- `mark_updated`
- `mark_confirmed`
- `mark_resolved`
- `get`

Memory 侧提供对应的组织级能力，但不拆成大量细粒度工具。

## 9. 错误处理与幂等

- 如果线程创建成功但卡片发送失败，线程仍保留，后续可重试。
- 如果卡片更新失败，必须继续沿用 `current_card_id`，不能新建重复卡。
- 如果条目写入成功但状态更新失败，后续应可根据版本重试。
- 所有写操作应围绕 `arrangement_id` 幂等化。

## 10. 测试

重点覆盖：

- 阻塞 / 非阻塞 / 纯记录三类判定
- 原始答复版本追加，不覆盖旧版本
- `arrangement_id` 绑定与 `task_id` 后绑
- 安排者与接收者字段级可见性
- 安排者补充后进入 `updated_waiting_recipient_confirmation`
- 接收者确认前不自动恢复执行
- 单卡片原位更新，不重复发送

## 11. 实现注记

- `feedback_thread` / `feedback_entry` 只是规范名，实际表名或模型名可按各自 workspace 的既有命名风格收敛。
- 线程卡片的视觉排版沿用现有飞书卡片样式，不在本设计里展开。
- Agent 侧保持单一反馈入口，Memory 侧保持单一组织级反馈管理入口，二者都以动作参数区分生命周期阶段。
