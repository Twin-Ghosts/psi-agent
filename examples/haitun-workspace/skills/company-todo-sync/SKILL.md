# 公司 TODO 周期同步（采集 → 建树 → 报表 → 派发）

一个周期跑一次,顺序固定:**采集 → 判假 → 建树 → 台账 → 报表 → 派发**。
本技能只管这条正向流水线;闭环判定与回流在 [`company-todo-audit`],mentor 打分回写在
[`company-todo-review`]。

先读一次 [`feishu-todo-board-sync`]:那份技能的三条硬规则(结构现场探、按 @人名 归属、
非空单元格先报警不覆盖)在本技能里继续有效,不要重写解析逻辑。

## 四个存储各自的权威边界

同一份信息只认一个权威源。两处不一致时按这张表裁决,不要自己挑一个看起来对的:

| 存储 | 权威内容 | 谁写 | 冲突时以谁为准 |
|---|---|---|---|
| 飞书文档表格 | 每人填报的原始目标与 todo 文本 | 员工人工填写 | **原始文本**以它为准 |
| LLM wiki | 工作树结构、历史快照、mentor 评价 | agent 写;人可随时改 | **目标口径**以它为准 |
| Bitable 台账 | 结构化 todo 行、状态、打分 | agent 写 | **统计与筛选**以它为准 |
| 飞书任务 | 某条 todo 到底交付没有 | 执行人勾选 | **交付状态**以它为准 |

boss 是根节点:**不写 todo、不收派发**,只收整体统计。

## 1. 采集

1. 表格挂在 wiki 下时,先 `feishu_api` 打 `GET /open-apis/wiki/v2/spaces/get_node`
   (`query_json='{"token":"<node token>"}'`),`obj_token` 才是 spreadsheet_token。
2. **列定位用 `feishu_sheet_find_columns`,不要数表头**。它按代码判定每列语义:
   `kind: "date"` 的列带归一好的 ISO `date`,`"names"` 是人名列,`"mentor"` 是 mentor 列。
   数表头是已经出过事的失败模式。
3. 取本周期的列:在 `date` 里找今天;找不到就取最接近的一列,并在报表里写明
   「按 08-05 列读取」—— 不许悄悄换列。
4. 读值用 `feishu_sheet_read_grid` 分块读,**读到 `has_more` 为 false 才算读完**。
   它带 `next_start_row`;半途停下就是拿残缺数据下结论。窄区间可以用 `feishu_sheet_read`。
5. 解析分层:按缩进与关键词切成大目标 / 小目标 / todo 三级,各自抽截止日期与验收人。

### 解析字段规范

| 层级 | 必填 | 选填 | 缺失时处理 |
|---|---|---|---|
| 大目标 | 标题、截止日期 | 友商对比、外部成果(用户数/金额) | 入库并标「待补」,报表高亮 |
| 小目标 | 标题、截止日期 | 所属大目标 | 无归属则挂到该人当期唯一大目标 |
| todo | 标题、截止日期、验收人 | 所属小目标、成果物形式 | 缺验收人取该人 mentor 兜底 |

两条不许放宽的:
- 缺字段标 `needs_fix` **照常入库**,不静默丢、也不阻塞流水线。
- 验收人由 mentor 兜底时,在报表里标「验收人由 mentor 兜底」,给 mentor 纠正的机会。
- 大目标缺「友商对比」或「外部成果」时标「待补」——这两项是大目标的必填字段,但缺失
  不阻塞整条流水线。

### 真实写法(同一个人不同周期就会换,两种都得认)

实测同一格里出现过两套写法,**按一套写死会漏掉大半内容**。已核实的形态:

```
<领域标题>                           <- 在任何层级段头之前,不是层级项
大目标：<目标标题>                     <- 标题跟在冒号**同一行**
      时间：12月                     <- 截止日单独一行,可能只有月份
      闭环：<闭环描述>                 <- 带标签的说明行
      标准：
     （1）<标准条目>                   <- 归到上面那个条目
        友商对标：<友商名与数据>          <- 大目标的「友商对比」原文在这
小目标 & 闭环                        <- 段头可能带后缀
1.<小目标标题>
      时间：8.7
TODO ：                             <- 冒号前可能有空格
1.<todo 标题>【紧急】
      时间：8.7
      验收人：<姓名>                   <- 显式验收人,别当成说明丢进评语
```

另一套(较早的周期)把截止日写在标题里:`1. <标题>（7.30）；`,段头「大目标：」独占一行、
标题在下一行。

解析要点,每一条都是实测踩过的:
- 截止日**两种来源**:标题里的 `（8.7）`,和单独一行的 `时间：8.7`。只认前者会让整格
  报「缺截止」。
- `时间：12月` **只有月份**:按那个月**最后一天**算(大目标的口径是「年底前」),取 1 号
  会把没到期的目标算成逾期。
- 无年份的 `8.7` 用周期所在年份;比周期早半年以上的按次年算(跨年填法)。
- `验收人：` 是**显式字段**,抽进验收人而不是评语 —— 抽错就等于把有验收人的 todo 判成
  缺验收人、白走一次 mentor 兜底。
- 「外部成果」要的是**可度量的数字**(token/留存/用户数/金额),不是闭环描述。只按关键词
  匹配会先撞上「闭环:…用户用它…」这类句子 —— 要求同时含数字。
- 段头判定用「行首是否以该词开头」,别用整行相等:`TODO ：`、`小目标 & 闭环` 都不等于
  裸词。

## 2. 判假(必须在派发之前)

`feishu_leave_query(approval_code=<假勤审批定义码>, date_from=<周期首日>, date_to=<周期末日>)`。
请假事实**直接来自飞书审批** —— 工具枚举该定义下窗口内的实例,逐条读出申请人与起止日期。
不需要任何人再把请假填进表格。

`approval_code` 是**审批模板**的编号(不是某一次申请的编号),所以它是**一次性配置**,
不是每周期的人工动作。本租户已探明的三个:

| 模板 | approval_code |
|---|---|
| 请假(Leave) | `99EEC396-536A-4C7A-8B2D-412584E35CE3` |
| 补卡(Clock-in/out Correction) | `09D3F0F3-2A0B-4E05-B40D-9D5565D2A27B` |
| 报销(Reimbursement) | `5F444354-FFC3-4509-8817-D02A18B414CD` |

判假用**请假**那个。换租户或模板被重建时重新探一次:`feishu_api` GET
`/open-apis/approval/v4/tasks/query`(带 `user_id`、`topic=3` 我发起的),返回里每条的
`definition_code`(有的给 `process_code`)就是它 —— 别用 `process_id`,那是实例编号。

判定口径在工具里固定,**不要自己心算日历**。按结果分三种处理:

| 情形 | 卡片与任务 | 台账状态 | 报表呈现 |
|---|---|---|---|
| 整周期请假(`full_period_applicants` 命中) | 不派卡、不建任务 | 请假顺延 | 该人整块标「请假」,不计入逾期 |
| 部分日期请假(`hit_days` > 0) | 照常派,截止日顺延请假天数 | 请假顺延 | 该条标「截止顺延 N 天」 |
| 请假中已交付 | 照常,不特殊处理 | 按实际状态 | 不标请假 |

三条要知道的:
- **只算已通过**的申请。`skipped_not_approved` 是本次跳过的待审批/被拒/撤回条数 ——
  这个数大得异常就去看审批是不是卡住了,别当成「没人请假」。
- `needs_fix` 是抽不到日期的申请:提示 mentor 复核,不要当成「没请假」。
- **没走审批流程的请假查不到**(口头请假、HR 后台直接改的),按未请假处理、由本人当场
  申诉。这是本方案接受的边界:与其让整条流水线依赖「必须有人记得填表」,不如让漏走
  审批的那个人当场说一句。
- `on_leave` 里的 `applicant` 是 id 不是姓名。要展示给人看、或要跟表格里的人名对上,用
  `feishu_api` GET `/open-apis/contact/v3/users/batch`(`user_ids` 重复同名 key 传多个,
  一次 ≤ 50)一批换成姓名,别逐个查。详见 [`feishu-contact`]。

## 3. 建 wiki 工作树

树靠 `[[双向链接]]` 表达,不靠目录层级 —— `wiki_links` 能直接 traverse,目录嵌套在
wiki 工具里没有对应查询。tags 统一打三类:`person` / `cycle` / `project`。

- 人员页《张三》:正文首段写「上级:[[李四]]」「下属:[[王五]]、[[赵六]]」,
  其后是「当前目标」区块与按时间倒序的「历史索引」区块。
- 组织根页《公司工作树》:只放 boss 一个链接与一句读法说明,作为遍历入口。
- 周期索引页《TODO 周期 2026-08-05》:列出本次覆盖的所有人链接与本次统计数。

**只在 mentor 列出现、自己没有数据行的人也必须建页。** boss 就是这样(方案里 boss 不写
todo,所以他不在表的人名列里),漏建会让所有下属页的「上级」链接变成断链 —— 实测建成时
23 条断链全指向 boss。建完用 `wiki_links` 抽查 `broken` 应为空。

散文里举例说明 wikilink 语法时别写成真的双括号:那会被索引成一条指向不存在页面的链接
(实测根页因此多出一条 `broken`)。

### 只增不覆盖(本节最关键)

`wiki_write` **只有整页覆盖、没有 append**。所以「只累加」由本技能保证:

1. 每周期为每人写一页**独立快照页**《张三 todo 2026-08-05》,内容是该次填报的完整
   目标与 todo。这一页此后不再被任何自动流程改写。
2. 人员汇总页《张三》**只改「历史索引」区块**:先 `wiki_read` 取回全文,在索引区块
   顶部插入一条 `[[张三 todo 2026-08-05]]`,**其余字节原样写回**。
3. 幂等:快照页 slug 相同,重跑覆盖同一次的内容;汇总页发现索引已有该条则不重复插入。
4. **同一个人的汇总页不要并发改写** —— 后写的会整页覆盖先写的。按人**串行**处理。

人工改目标不会被冲掉:人改的是「当前目标」区块,自动流程只碰「历史索引」区块,两者不
重叠。每次写入前 `wiki_read` 一次,把人工改后的「当前目标」读进上下文作为本次报表口径,
所以人改完立刻生效。历史快照页原则上不改;确实填错了就直接编辑那一页,下次运行不覆盖它。

## 4. per-mentor 台账

`feishu_mentor_ledger_ensure(mentor_open_id=..., mentor_name=..., folder_token=...,
boss_open_id=..., template_app_token=...)`。每个 mentor 一张**独立 base**,不是一张大表
加筛选视图 —— 筛选视图不是权限,拿到链接就能看到整表;行级隔离要自定义角色,而自定义
角色要先开高级权限,base 在 wiki 里或被嵌进文档时开不了(1254301)。

- 工具是**幂等**的:连跑两次只有一张台账。每周期照常调用,`created` 会告诉你是新建还是复用。
- 授权**只加不减**:mentor 编辑、boss 只读。`unexpected_members` 里是目标之外的既有
  协作者 —— 报给用户,不要自己撤(撤权不可逆)。机器人不作为协作者加,它靠 `user_key`
  的授权访问。
- 生产路径应当维护一份**列已建好的模板 base**,把它的 app_token 传 `template_app_token`
  (复制只带结构)。不给模板会建出一张只有占位列的空 base,列得另外补。
- mentor 换人或下属调整时**重跑本工具**:授权按新名单收敛,历史数据留在原 base 不迁移。

### 本租户已建好的(直接用,别重建)

| 用途 | token |
|---|---|
| 台账文件夹 | `BJo2flBgyl5Of0dymLocw3YPnjc`(「Mentor TODO 台账」) |
| 台账模板 base | `A3ifbY8amaTNijsDL5Uc0FQfnnh`,表名 `TODO台账` |

建模板时的两个坑(已踩过):
- **第一列必须是可当索引列的类型**(文本/数字/日期/电话/超链接/公式/地理位置)。
  「负责人」是人员类型(11)**不能**当第一列,飞书报 1254012 —— 所以让「标题」领头。
- 飞书建 base 时自带一张占位表(名为「数据表」),不删会和真表并存,`table_name` 解析
  时容易撞上。建完真表就把占位表删掉。

写入时的字段形状:日期列要**毫秒时间戳**(不是日期串),人员列要 `[{"id": "ou_..."}]`,
单选/多选要写选项名。列名对不上会被飞书**静默丢弃**(返回 code:0 但值没写进去),所以用
`feishu_bitable_create_records` —— 它会比对请求与返回,把丢掉的列报成 `dropped_fields`。

台账列(建模板时按这份建):

| 字段 | 类型 | 说明 |
|---|---|---|
| 周期日期 | 日期 | 本次采集的周期,如 2026-08-05 |
| 负责人 | 人员 | 写这条 todo 的人,也是被派发对象 |
| mentor | 人员 | 验收人 |
| 层级 | 单选 | 大目标 / 小目标 / todo |
| 父项 | 文本 | 所属上级目标标题,用于还原三级结构 |
| 标题 | 文本 | 目标或 todo 正文 |
| 截止日期 | 日期 | 自设交付时间点 |
| 状态 | 单选 | 待开始 / 进行中 / 已交付 / 已闭环 / 未闭环逾期 / 请假顺延 |
| 闭环五要素 | 多选 | 勾齐五项才允许置为「已闭环」 |
| mentor 打分 | 数字 | 1-5,**权威分** |
| agent 建议分 | 数字 | 1-5,仅参考,不覆盖 mentor |
| mentor 评语 | 文本 | 回写 wiki 的原文 |
| 外部成果 | 文本 | 大目标专用:用户数 / 金额 |
| 友商对比 | 文本 | 大目标专用 |
| 任务 GUID | 文本 | 对应的飞书任务,交付状态回查用 |

写入用 `feishu_bitable_create_records`(**列名对不上会被静默丢弃**,所以先确认列名一致);
清默认空行用 `feishu_bitable_clear_table`。

## 5. mentor 报表

每个 mentor 只收**自己下属**的:按 `mentor_open_id` **私聊**推送,不进群、不群发。
台账链接 + 一张统计卡摘要。统计卡内容:本周期大目标/小目标/todo 各多少条、已闭环多少、
逾期多少、请假顺延多少、下属平均分。统计图用 `feishu_chart` 渲染 PNG 附在卡片里。

高亮两类:标「待补」的大目标(缺友商对比/外部成果)、标「验收人由 mentor 兜底」的 todo。

boss 单独一张全公司汇总 base(只读)+ 一张整体统计卡。跨 mentor 的统计要**逐个 base 读
取后合并** —— 这是为「互不可见」付的确定代价,不是一次查询能拿到的。

## 6. 派发(顺序不能颠倒)

1. **先建飞书任务**:每条 todo 打 `feishu_api` `POST /open-apis/task/v2/tasks`,
   拿回 `task_guid`,把截止时间写进 `due`(毫秒时间戳)。细节见 [`feishu-task`]。
2. **再发 TODO 卡**:`feishu_todo_card_send(receive_id=<负责人 open_id>, items_json=...)`,
   把 `task_guid` 填进对应行。一张卡列他本周期全部 todo,每行独立勾选、勾一条只结一条、
   卡片原地更新。上限 40 条,超了拆卡。
3. **回写台账**:把 `task_guid` 存进「任务 GUID」列,供后续查交付状态。
4. **建截止提醒**:每条 todo 用 `schedule_manage` 建 `once_at` 的一次性提醒,截止前一天
   私聊提醒本人。一次性任务**必须 `fire=tool`**(框架不接受 prompt 型一次性任务)。

顺序理由:卡片行链接指向任务,任务不存在就没有可点的目标。行标题用官方 applink 协议拼
(`task/v2` 的返回体里没有 web URL,别等它)。这个 applink 尚未用真实 task_guid 实测,
试运行时验证一次。

回流项(来自 [`company-todo-audit`])也在这一步派发:标题前缀「[逾期 N 天]」,
原截止日保留在正文里,**不许静默改截止日**。

## 需要的权限

`sheets:spreadsheet`(读表)、`bitable:app`(台账)、`drive:drive`(建 base、加协作者)、
`task:task`(建任务)、`im:message`(发卡)。机器人要是那张 todo 表格的协作者,或由
`feishu_auth_start` 拿到 user token。台账所在文件夹要能被 `user_key` 那个人建文件。
